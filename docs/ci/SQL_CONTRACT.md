# Reviewing a migration: the effective contract and the applied baseline

Migrations are the history; the database they build is the contract.
Since #1455 the quality workflow writes both halves of that contract
down, so a reviewer reads what a change *produces* instead of replaying
fifty anchored patches in their head.

## `assets/instance/contract.txt` — the effective contract

Generated by `quality · database` after the replay from empty
(`scripts/contract_check.sh`), committed, and gated: the job fails when
the replay disagrees with the committed file, and the diff in the log is
the review.

One line per object of the `public` schema, sorted:

```
routine public.open_payment_intent(p_workspace_id uuid, p_member_id uuid, p_provider text, p_period text, p_amount_cents integer, p_currency text) -> TABLE(id uuid, reference text) | function | definer | volatile | exec:authenticated,service_role | body:5c1f2a9d0b3e
constraint public.payment_intents.payment_intents_member_id_same_workspace FOREIGN KEY (workspace_id, member_id) REFERENCES members(workspace_id, id) ON DELETE CASCADE
trigger public.payment_intents.payment_intents_ledger_matches CREATE TRIGGER … BEFORE INSERT OR UPDATE OF ledger_entry_id, workspace_id, member_id, amount_cents ON public.payment_intents FOR EACH ROW EXECUTE FUNCTION payment_intents_ledger_matches()
```

- **An anchored patch appears**: it changes the body, so the routine's
  `body:` digest moves, and the diff names the routine.
- **A stale overload appears**: it is a second `routine …` line with the
  same name and different arguments.
- **A grant appears**: `exec:` lists exactly `anon`, `authenticated` and
  `service_role` as they may execute.
- **A constraint or trigger change appears** as its own line.
- Nothing unstable enters the file: no OIDs, no timestamps, no owners.

Two replays of the same migrations produce the same file. The full
definitions — every body, not only its digest — are the run's
`effective-schema.sql` inside the `quality-database` artifact.

## `supabase/APPLIED.sha256` — the protected baseline

An applied migration is history. `dart run tool/record_applied_migrations.dart`
records the digest of every file applied to the reference project, and
`test/lint/applied_migrations_immutable_test.dart` fails when a recorded
file changes or disappears, or when a file is inserted **below** the
highest recorded number. A file above the baseline is a branch's draft
and is free until it is applied — the state the issue asked the rule to
distinguish.

The ritual, after `apply_migration` on the reference project: run the
recorder and commit `APPLIED.sha256` in the same pull request as the
migration. A correction to an applied migration is a forward migration.

## A worked example: from a migration to the caller identity contract

`open_payment_intent` is created in `0165_number_sequence_adopters.sql`
and rewritten by `0210_definer_caller_guards.sql` to check
`my_active_member(p_workspace_id)`, which reads `auth.uid()`. The
contract line says what the reviewer needs without either file:
`definer`, `exec:authenticated,service_role`, and a body digest that
moved in the pull request that landed 0210.

The other half of the contract is the caller. `my_active_member` needs a
user in the JWT; a service-role call carries none. That is the #1450
defect: `create-payment-order` verified the caller's token and then
opened the intent through the service-role client, so every payment
answered `intent_open_failed`. The Edge function now opens the intent
through a client that carries the caller's token, and
`scripts/edge_payment_check.sh` runs the real handler against the replay
on every pull request. When the `exec:` list or the `definer` marker of
a routine an Edge function calls changes in this file, that check is the
one to read next.
