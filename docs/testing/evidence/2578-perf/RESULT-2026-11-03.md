# #2578 performance evidence, run 2026-11-03 (local database)

This is the run of `2578-explain.sql` that `PROVENANCE.md` listed as NOT RUN. It ran on a throwaway
local Postgres (the repository's migrations replayed by `supabase db reset --local`). **The function
state of the recorded run is 0662 applied, 0663 NOT yet written**: results 1-3 below, including the
page timings and the failing check B13, are the state after 0662 and before 0663. 0663 was written
because of B13 and is proven by pgTAP 348 only; the full proof was not re-run after it. The run was
not on the dev project: the dev project's request limit (about 100 s) cuts
the seed. Machine: a Mac mini, a 4 GB / 2 CPU virtual machine (Colima), Postgres 17 as shipped by the
Supabase CLI. Dataset: 601,344 reservations, 1,500 seats, 402 members, 14,400 invoices (result 1); no real data.

## How this run differs from the committed proof file (read before trusting a number)

* The seed is run in ONE transaction and COMMITTED, then `ANALYZE` is run, then the steps run as
  separate statements. A single rolled-back transaction has no planner statistics for the rows it has
  just inserted: the first attempt (unmodified file, rolled back) spent more than 20 minutes in its
  first step on plans no installation would get. Planner statistics are what a real workspace has.
* The seed statement timeout was raised from 120 s to 900 s (the seed took 205.8 s in total; one chunk
  exceeded 120 s while the machine was short of memory).
* The step queries, the bounds and the checks are the committed file's, unchanged.
* "Cold" means the first call of the session after the seed and ANALYZE; shared buffers are warm.

## What the proof found (and what was changed)

1. **Capacity figure, one call.** On analysed data one month cost 6.2 s with the old definition and
   0.39 s with the new; the 400-day maximum window 107.7 s and 3.2 s. Cause: the reservations were
   joined to the seats' history rows on four OR-ed keys (a nested loop with a join filter, reservations
   x seats) and each seat then scanned the whole joined set twice. Fix: migration 0662, four hashable
   joins and one per-seat aggregation. The old and new answers were compared on four windows (a week
   now, a week in March, a week with a level filter, a 52-hour window across two days): identical.
   (An earlier figure of 225 s, taken before statistics existed, was wrong and is withdrawn.)
2. **Check B13 failed.** An analyst without finance rights sending the whole 60-request page was
   answered with 11 capacity figures and 49 answers "over budget" instead of being refused whole,
   because the time budget was checked before the reader's own refusal. No finance value was returned,
   but the contract is "refused whole". Fix: migration 0663 checks the rights of every distinct metric
   before the first figure; pgTAP 348 is red without it and green with it.
3. **The page at this dataset size.** One page of 60 requests runs into the 4000 ms budget on this
   machine: 11 figures are computed, 49 are answered as over budget (54000), by design. A page that
   should be complete needs either a faster machine or a smaller page; the budget and the page size are
   the workspace settings `bi.batch_time_budget_ms` and `bi.batch_max_requests`.

## Limitations

* One machine, a virtual machine with 2 CPUs and 4 GB: the times are what this machine measured, and
  say nothing about another server. The old-versus-new ratios were measured on the same machine and
  dataset. No SLA is claimed.
* Shared buffers were warm; a cold operating-system cache cannot be produced here.
* The memory column is the backend's context total, not its peak.
* Cancellation: `cancel page at budget` was cancelled with 57014 after 4003 ms under a 4 s
  statement_timeout, as designed.
* The data is synthetic: one workspace, one booking per member and half-day pattern, invoices one per
  member-month.

* Equivalence of the four-key join with the old OR join: the old and new answers were compared on
  four real windows (seat targets only), and pgTAP 347 exercises a seat target and a level target
  separately. A pair of a reservation and a seat matching on more than one key is not exercised by a
  fixture: a reservation names at most one target key (a deleted place keeps a label and none), so such a pair does not arise; the NOT-COALESCE
  guards of the later branches only make the equivalence hold by construction for NULL keys.
